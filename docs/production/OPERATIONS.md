# Development, production, backup and release runbook contract

These are requirements for scripts and runbooks the implementation agent must build and test. They are not commands already run against GCP. Do not replace placeholders with guessed cloud resources, domains, credentials or volume names.

## 1. Two environments, independent data

| Concern | Local development | Production |
|---|---|---|
| Application URL | Recommended `https://talent.taleed.test`; mapped to loopback | Verified approved hostname on the chosen static IP; direct-IP TLS only through a verified supported arrangement |
| Database | Independent developer/worktree MySQL database and volume | Fixed authoritative Talent production database and external storage identity |
| Secrets / APP_KEY | Generated once per local installation, locally ignored | Stable protected production values; never regenerated by a code release |
| Content / files | Synthetic fixtures or authorized non-private source copies | Live approved catalogue/CMS content, sources, uploads and reports |
| Mail | Mailpit; no real recipients by default | Approved SMTP transport/domain; real sends require authorization |
| Updates | Local source mounts and Vite HMR | Immutable built release; no source bind-mount from Git |
| Reset | Explicit local-only command, blocked for production identities | No reset, fresh migration, destructive seed or local DB import |

CI databases are ephemeral and synthetic. A recovery rehearsal is an isolated operations task, not a persistent staging environment or a public pre-production service. Do not create staging DNS, secrets, pipelines or resources.

## 2. Local Docker and HTTPS

Provide `compose.dev.yaml`, documented `.env.example`, a versioned Dockerfile, a Makefile or equivalent scripts and a concise local README. Target commands such as `make dev-init`, `make dev-up`, `make test`, `make dev-down` and an unmistakable `make reset-local-synthetic` are interfaces to implement and test, not commands presently available in this archive.

Development services include PHP/Laravel/Statamic, MySQL 8.4 LTS, the local reverse proxy, Vite HMR, worker, scheduler and Mailpit. Support the user's likely macOS/Apple Silicon and Linux environments by verifying image architecture and file permissions; don't silently force slow emulation unless documented. Keep dependency installation reproducible and service health checks realistic.

Use a hostname under `.test`, e.g. `talent.taleed.test`, with explicit loopback resolution. Generate a certificate using a local CA tool such as mkcert and document installing its trust certificate on the host/browser. Ask permission before changing host trust/hosts files. Never commit CA private keys or leaf private keys, bake them into images, or instruct developers to disable TLS verification. Mount only the needed leaf certificate/key read-only into the local proxy; the CA private key stays outside the container.

Proxy `/api`, auth, CSRF and application routes through the same HTTPS origin. Proxy Vite HMR with WebSockets over TLS and configure the correct external hostname/port. Avoid credentialed wildcard CORS, mixed content and browser requests to `http://mysql`/internal Docker hostnames. Bind development admin/database ports to loopback only when genuinely necessary.

A new local checkout runs migrations and explicit local synthetic factories against its own verified local identity. Starting an existing checkout never reseeds or erases it. Provide a documented server-saved draft test across browser refresh and container recreation. Keep privileged synthetic accounts local-only with obvious labels; production builds must not bundle their password fixtures or persona switcher.

## 3. Verify the chosen GCP VM and edge before changing anything

With explicitly authorized read-only infrastructure access, record the actual GCP project, VM, zone, static-IP resource/address, disk names and mount identity, service account, firewall/IAP access, existing containers/networks/volumes, reverse-proxy routes, certificate renewal mechanism and available memory/CPU/disk. Record identifiers in private operator configuration or sanitized evidence, never credentials. Distinguish the same project from the same VM.

Do not assume the Sustainability repository's diagnostic VM is also Survey's VM. The user wants one approved instance for this Talent deployment; verify which existing target is intended. Do not provision a new second VM or move live sibling applications without explicit approval. If sharing the chosen VM exceeds safe resource headroom, stop the deployment gate and report measured capacity plus options; do not silently change the architecture or degrade other tools.

Exactly one approved edge owns host ports 80/443. Add a Talent hostname/upstream while preserving current default-IP and sibling virtual hosts. Validate configuration before a controlled reload and smoke-test existing tools before and after. A code release must not restart unrelated services or replace the shared proxy's whole configuration directory.

Prefer a dedicated Talent hostname pointing to the same static IP. Use distinct host-only cookies and isolated credentials/storage. Direct-IP HTTPS is technically available through supported short-lived certificates, but requires matching client support, reliable renewal and expiration monitoring; do not claim it is impossible or that an ordinary domain-certificate configuration covers an IP automatically. Distinct apps on one IP still need a routing scheme; do not silently force a path-prefix migration of existing apps.

Trust only the controlled proxy path. Verify forwarded scheme/host handling, secure cookies and signed email links behind TLS. A wildcard trusted-proxy setting from a sibling file is not a reusable proof of safety in a different topology. Keep MySQL unexposed on the public interface and off the edge's broad service network. Restrict SSH using the approved IAP/firewall approach; no Docker TCP socket or public phpMyAdmin.

## 4. Make data lifecycle independent of code lifecycle

Preferred implementation: `compose.prod.data.yaml` owns the database lifecycle and its private data network; `compose.prod.yaml` owns web/worker/scheduler and one-shot app operations. Both refer to explicitly provisioned production storage/network identities. A reviewed equivalent single-file/profile design is acceptable only if the deploy path cannot recreate, upgrade or replace the database unintentionally. Do not let a generic unscoped `docker compose up` deploy all services indiscriminately.

Use an independently managed persistent data disk mounted at a verified fixed host path where the existing host design permits it. Ensure the disk is not casually deleted with an application VM replacement, and verify mount identity before Docker creates/writes data. External Docker volumes alone do not prove which disk holds their data. A missing mount must not make Docker write a new empty database onto the boot disk. Implement and test VM boot/reboot ordering so Docker cannot auto-start MySQL against a fallback boot-disk path before the real data disk is mounted. Deployment-time checks alone are insufficient; service startup and restart behavior must enforce the same storage guard.

A production Compose reference must require existing storage rather than silently create a new volume, for example:

```yaml
# Illustrative invariant; the implementation must connect the actual services.
volumes:
  talent_mysql:
    external: true
    name: ${TALENT_MYSQL_VOLUME:?An existing production volume is required}
```

External volume names are fixed operator configuration, not derived from a developer's branch/checkout name. Verify expected mount/device, volume labels/identity, `installation_identity.dataset_uuid`, database name and stable key-version references. Refuse to run the regular release path when any identity is missing or wrong. Never use `APP_ENV=production` as the only protection check.

Persist MySQL data, private storage/uploads/reports, actual editable Statamic content, single CP user and any real runtime asset paths. TLS state belongs to the existing edge's operations plan, not a disposable frontend container. Do not persist compiled `bootstrap/cache`, old config/view caches or code directories across releases. Rebuild derived caches per release, with appropriate content invalidation after CMS edits.

Provide a separate one-time `init-production` workflow: only after authorization, verify a genuinely empty new Talent target, provision correct storage identities, initialize MySQL, generate/store stable keys once, run initial migrations and create the first administrator through a secure operator flow. No shared default password. Install only approved reference content explicitly. Repeat invocation on a populated target must fail, not “repair” it by resetting data. The normal deploy/entrypoint never calls this initializer as a fallback.

## 5. Secrets and permissions

Keep real environment configuration outside Git and images, with restrictive ownership/permissions or an approved secret manager. Production keys must survive releases and VM recovery; key rotation is a separate documented operation with key-version/decryption tests. Do not log full environment/Compose expansion or copy secret files into CI artifacts. Scripts must avoid shell tracing and command-line password leaks.

Use distinct credentials for application runtime DML, schema migration and backup/provisioning where feasible. Never grant the app MySQL root or access to sibling databases. Separate roles for backup creation and destructive retention/recovery reduce compromise impact. CI authentication to GCP should use restricted short-lived OIDC/workload federation where the approved setup supports it, bound to the exact repository/ref and protected release process, not a committed service-account JSON key.

Use an allowlisted secret inventory in documentation: variable name, purpose, owner, storage location reference and recovery procedure, not value. Root DB credentials, SMTP secrets, OAuth/WIF material and APP_KEY do not belong in agent chat or plaintext backup manifests. A reference to a recovery secret is not enough until restore access to that secret has been tested by the authorized operator.

## 6. Repeatable release transaction

Build candidate images outside the live service where possible, after successful CI, from an exact reviewed commit and real lockfiles. Record immutable image digest/release identity. A VM-side build from an exact CI-passing archive is an alternative only with resource isolation/headroom and a recorded artifact identity; no mutable `git pull` build inside live containers.

The deployment script must implement these ordered steps:

1. **Preflight and lock.** Validate the allowed target, immutable release, available capacity, expected storage/DB/key identity, image availability and prerequisite approvals. Acquire one bounded host-level coordination lock covering deploy/migrate/backup. Avoid a backup subprocess trying to reacquire its caller's non-reentrant lock. Define safe standalone and inherited-lock modes.
2. **Create a consistent recovery point.** Pause Talent write paths, its worker/scheduler and content/import writers as required. Explicitly block CP writes as well; do not assume standard application maintenance automatically blocks every Statamic/admin route. Other Taleed tools remain unaffected. Drain jobs safely and establish a documented DB/file consistency boundary.
3. **Back up and verify.** Complete database + runtime-files + protected key-recovery set. Verify checksums/completeness and the required off-VM copy. Fail closed on any required missing volume, file component, key access or offsite error. Do not migrate after a merely started or partially uploaded backup.
4. **Migrate once.** Run one reviewed migration task using the candidate release and migration identity. Prefer additive/expand changes, bounded backfills and later explicit contract cleanup. Database-cache locking may not exist on first install; the host lock is the primary release guard. Do not launch migrations concurrently from app/worker/scheduler entrypoints.
5. **Replace app services, not the database.** Replace web/worker/scheduler with the accepted release, using the same persistent identities and keys. Build release-local caches. Verify queue compatibility and precisely one effective scheduler. Database upgrades and shared edge modifications are separate maintenance operations.
6. **Verify and reopen.** Check HTTPS, `/app` deep links, safe liveness/readiness, release identity, authentication, DB connectivity, private storage, scheduler heartbeat and queue behavior. Run approved synthetic smoke checks. Reopen Talent writes only after success, then check sibling tools remained healthy. Record release/backup IDs and operator outcome.

Scripts need `set -euo pipefail`-equivalent behavior, safe quoting, bounded retries/timeouts and failure traps. Validate input identifiers instead of evaluating arbitrary environment/JSON/shell text. Report whether maintenance remains enabled after failure and exactly what the operator must do; do not conceal a failed release behind an unconditional success message. A failed migration must not trigger an automatic DB rollback/restore.

Use short maintenance windows rather than promising zero downtime on a single VM. Test the release procedure with populated synthetic data through at least two application versions, not only first install.

## 7. Backup completeness and off-VM recovery

MySQL needs a database-aware consistent backup. A transactional logical dump of InnoDB can be appropriate at this scale; avoid concurrent DDL during the dump. A tar of the running MySQL data directory is not an acceptable recovery guarantee. Disk snapshots can supplement, not replace, a tested application-consistent recovery set.

Coordinate database and mutable file/CMS writes. Immutable content-addressed source objects plus a transactionally consistent reference snapshot simplify consistency, but private report deletions, CMS edits and uploads still require an explicit capture policy. Don't compare row counts taken after a live dump and claim they represent its exact snapshot; derive/check a coherent manifest or verify counts during controlled capture/restore.

Each recovery set identifies the dataset, release, schema migration state, database dump, runtime file archives, CMS content/user, file checksums, key-version recovery references, creation time, consistency method and actual offsite status. The offsite checksums must match the files actually included after secret/config exclusions. Verify the uploaded artifact independently and mark partial/failed sets unfit for deployment/recovery. No false success when offsite storage is unconfigured or upload fails.

Store encrypted backups off the VM in an approved GCS region/bucket with private IAM, lifecycle/retention and deletion controls approved by the data owner. Restrict routine backup-writer deletion capability; validate a protected retention/restore identity. Do not make an irreversible bucket retention lock or purchase new resources without approval. Store needed keys in a separate protected recoverable location; losing them can make encrypted records unrecoverable even when SQL restores successfully.

Recommended initial service target for approval: nightly complete backups plus a complete pre-release set. This can still lose changes after the latest backup. Agree a maximum RPO and measured RTO; a proposed 24-hour RPO/4-hour RTO is a starting discussion, not a guaranteed result. A shorter RPO needs implemented and tested measures such as frequent off-VM binary-log archival. Binary logs kept only on the same disk do not protect against loss of that disk. Confirm retention, residency and privacy/deletion implications with the owner.

Alert on backup age/failure, missing offsite copy, disk pressure, queue backlog, worker/scheduler failure, application readiness and certificate expiry. Prove alert delivery, not merely YAML configuration. Logs and monitoring contain operational metadata, never private exercise contents or participation categories.

## 8. Restore and rollback

Build a restore workflow defaulting to an isolated target. Verify backup identity/checksums, compatibility, keys and target emptiness. Restore the database and associated file/key state, then check accounts, active drafts, pinned sources, recurrence history, closures, share statuses, owner-private decryption and file/report hashes. Prevent outbound mail, schedulers and live traffic on the rehearsal target. Replay privacy tombstones and membership/share revocations according to the recovery policy before reopening data access.

Use synthetic production-like data for developer recovery testing. A real backup restore is an explicitly authorized restricted operations exercise, not permission to copy live personal data to laptops or CI. Do not introduce a persistent staging service. Record actual recovery point, duration and success/failed checks. First release requires a documented rehearsal and an operator who can repeat it.

Rollback of **code** means redeploying the previous schema-compatible image while preserving current production data. If a migration is incompatible, choose a documented forward fix or separately approved recovery/promotion. Restoring yesterday's database as an automatic response to an application error can discard legitimate new writes and is prohibited. Restore/promotion commands must require exact target and backup identity plus explicit operator confirmation; never infer them from an ambiguous latest file.

## 9. Handover evidence

The final operator runbook must show real commands for initialize, start, update, backup, inspect, isolated restore and compatible rollback; verified environment names and storage identifiers; secret recovery ownership; DNS/TLS renewal and access procedures; tested monitoring; actual backup/restore evidence; expected maintenance window; and measured shared-VM resource headroom. Return a production URL only when the real HTTPS target was deployed and verified. Do not call the current Pages demo, a planned DNS name or local HTTPS a production result.
